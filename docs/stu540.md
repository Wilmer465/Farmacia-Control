# STU-540 — Integración directa por STU SDK

Firma en pad Wacom STU-540 sin Signature SDK ni SigCaptX: STU SDK (C API)
directo desde un helper nativo x64.

## 1. Piezas utilizadas (nada se instaló, copió ni registró de más)

| Elemento | Detalle |
|---|---|
| DLL | `C:\Program Files (x86)\Wacom STU SDK\C\bin\x64\wgssSTU.dll` |
| Versión | 2.18.0.82 (verificada en tiempo de ejecución por el helper) |
| Arquitectura | x64 (Electron 32.3.3 x64; helper compilado `/platform:x64`) |
| Mecanismo de carga | P/Invoke (`DllImport`, stdcall) con **ruta absoluta instalada** |
| Binding | C API directa (`WacomGSS_getUsbDevices`, `WacomGSS_UsbInterface_create_1`, `WacomGSS_Tablet_*`, `WacomGSS_InterfaceQueue_try_getReport`, `WacomGSS_ProtocolHelper_writeImage`) |
| Helper | `native/stu-bridge/stu-bridge.cs` → `native/stu-bridge/bin/stu-bridge.exe` |
| Compilador | `csc.exe` de .NET Framework 64 bits incluido en Windows (`C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe`). Sin descargas, sin NuGet, sin MSVC |
| Dependencias runtime | .NET Framework 4.x (preinstalado) + `System.Drawing` (Framework) |

Decisión técnica documentada: el COM `WacomGSS.STU.*` está registrado **solo
en 32 bits** (`HKLM\SOFTWARE\WOW6432Node\...` → `COM\bin\Win32\wgssSTU.dll`),
sin registro x64. Un proceso x64 (Electron) no puede instanciar ese servidor
in-proc. Por eso el helper es un proceso x64 aparte con P/Invoke a la DLL
x64 del binding C, que no requiere registro. No se usó `regsvr32`, no se
copió ninguna DLL, no se tocó `System32`, no se cambió ninguna versión.

## 2. Arquitectura

```
React (SignaturePad "Firmar en pad")
  ↓ window.api.firmaPad (preload/contextBridge, contextIsolation: true)
Electron IPC (firmaPad:detectar / firmaPad:capturar, con sesión validada)
  ↓ backend/controllers/firmaPadController.js
backend/services/signatureService.js (spawn + timeout + SHA-256 + sobre)
  ↓ stdio, UNA línea JSON
native/stu-bridge/bin/stu-bridge.exe (x64)
  ↓ P/Invoke STU SDK C API 2.18.0.82
STU-540 USB (VID 056A / PID 00A8)
```

El renderer nunca toca código nativo. El main nunca carga la DLL (vive solo
en el helper). El pad se abre con **bloqueo exclusivo**: una segunda captura
recibe `OCUPADO`.

## 3. Protocolo del helper

- `detectar` → `{ ok, dispositivos: [{ vid, pid, modelo, pantalla, sensor }] }`.
  Abre sin exclusividad, lee información/capacidad y cierra.
- `probar-pantalla` → escribe la pantalla de firma, espera 6 s, limpia y
  cierra. Diagnóstico sin interacción del usuario.
- `capturar --nombre X --documento Y --motivo Z [--timeout S]` →
  `{ ok:true, modelo, uid, origen:"STU-540", pngBase64, trazos, duracionSeg }`
  o `{ ok:false, codigo, error }`.

Pantalla a color de 16 bits (RGB565 big-endian, espejo de `flattenColor16`
del SDK): fondo blanco, título azul oscuro, texto negro, botón ACEPTAR verde
y CANCELAR rojo con texto blanco. Se usa `16bit_Bulk (0x12)` si hay endpoint
bulk, si no `16bit (0x02)`; la capacidad (`encodingFlag`, este STU-540 anuncia
`0x0F`) decide, con contingencia a 1 bit. Transferencia ~768 KB.
Tinta del entintado local fijada por protocolo: negra (`setHandwriting-
ThicknessColor`, grosor 3) sobre fondo blanco (`setBackgroundColor`), para
que el trazo en vivo se vea siempre igual.

### Cifrado v1 obligatorio (Diffie-Hellman + AES-128-ECB)

`Tablet::startCapture` del SDK exige handler de cifrado
(`Tablet.cpp:812-813`) y el STU-540 anuncia DH: el helper negocia el canal
antes de capturar, espejo de `Tablet_OpenSSL.cpp` del SDK, solo con clases
en-box de .NET Framework (`BigInteger`, `RNGCryptoServiceProvider`,
`AesManaged`), sin descargas:

1. `Tablet_getDHprime` (16 B big-endian); todo ceros = sin cifrado (contingencia).
2. `Tablet_getDHbase` (2 B); privada aleatoria de `p.bits-1` bits, pública
   `g^priv mod p` en 16 B.
3. `Tablet_setHostPublicKey` + sondeo de `Tablet_getDevicePublicKey` hasta
   clave no nula (réplica de `setHostPublicKeyAndPollForDevicePublicKey`).
4. Secreto `devPub^priv mod p` con relleno a 16 B → clave AES-128-ECB sin
   padding (claves limpiadas de memoria al terminar).
5. `Tablet_setPenDataOptionMode(None)` explícito + espera a estado `Ready`.
6. Arranque por `Protocol_setStartCapture` (el wrapper `Tablet_startCapture`
   es el que exige el handler; el protocolo acepta tras el handshake).
7. Sondeo de cola: reportes `0x10` → descifrado del bloque → `sessionId`
   BE32 verificada + **2 muestras de lápiz por reporte** en orden
   (`Protocol.hpp:1445-1462`); `0x01` solo en modo sin cifrado.

## 4. Almacenamiento (diseño actual + ruta futura)

Hoy la firma viaja como `data:image/png;base64` en `firma_data`, igual que el
canvas. Justificación técnica: pipeline existente validado de punta a punta
(validador, tope 2 MB por campo, listados sin blobs, reportes, app móvil) y
cero migración de esquema. Novedad: el sobre ahora incluye `sha256`,
`modelo`, `origen` y fecha para integridad y auditoría.

Ruta futura a archivo controlado (sin cambiar el helper): guardar el PNG en
`data/firmas/<orden>_<receptor>_<sha8>.png` y conservar en SQLite
identificador, ruta, hash, fecha/hora, usuario y orden/despacho. El sobre ya
trae todos esos metadatos.

En logs (helper y main) solo metadatos operativos: jamás coordenadas,
trazos ni imágenes (dato biométrico sensible, Ley 1581 de 2012).

## 5. Instalación / desinstalación / compilación

- Requisito en el PC: STU Driver + STU SDK 2.18.0 (ya instalados) y pad por USB.
- Compilar el puente: `pnpm run compilar:stu-bridge` (también corre solo como
  `prebuild` antes de `pnpm run build`). Salida ignorada por git:
  `native/stu-bridge/bin/`.
- Empaquetado: `extraResources` lleva `native/stu-bridge/bin` a
  `<resources>/native/stu-bridge`; el servicio resuelve la ruta según
  `app.isPackaged`.
- Desinstalar la integración: borrar `native/stu-bridge/`, revertir
  `extraResources`/`prebuild` y los canales `firmaPad:*`. El SDK de Wacom no se
  toca (es compartido con otras apps).
- Si falta el exe, la UI muestra: "Puente del pad no compilado. Ejecute:
  pnpm run compilar:stu-bridge".

## 6. Errores conocidos

| Código | Causa | Acción |
|---|---|---|
| `SIN_DISPOSITIVO` | Sin STU por USB | Conectar el pad / revisar cable y driver |
| `MODELO_NO_SOPORTADO` | Otro modelo STU | Solo STU-540 en esta fase |
| `OCUPADO` | Otro proceso lo abrió (p. ej. SigCaptX, demo) | Cerrar la otra app |
| `DESCONECTADO` | USB retirado / `device_removed` del SDK | Reconectar y reintentar |
| `TIMEOUT` / `TIMEOUT_LOCAL` | Sin interacción en el plazo | Reintentar (plazo 10–600 s) |
| `CANCELADO` | Botón Cancelar del pad | Flujo normal, sin error |
| `FIRMA_VACIA` | ACEPTAR sin trazos | Firmar de nuevo |
| `CIFRADO_NO_NEGOCIADO` | DH rechazado o sin clave del pad | Reconectar y reintentar |
| `CLAVE_INVALIDA` | Clave pública del pad fuera de rango | Reconectar y reintentar |
| `HELPER_NO_ENCONTRADO` | Sin compilar | `pnpm run compilar:stu-bridge` |
| `PAD_OCUPADO_LOCAL` | Segunda captura concurrente | Esperar a que termine la anterior |
| Apertura `rc=6` persistente | Pad colgado entre sesiones | Desconectar/reconectar el USB (verificado) |

Cierre ordenado: pausa de 300 ms entre `endCapture` y `disconnect` (el SDK
exige ~80 ms o el pad se cuelga hasta re-enumerar); apertura exclusiva con
3 reintentos cada 500 ms; una sola captura a la vez en el servicio.
| `ERROR_SDK` | SDK devolvió error | Ver detalle entre paréntesis |

Nota de implementación: tras `Tablet_attach` la tableta posee la interfaz; el
helper solo libera la tableta (liberar la interfaz aparte provoca
`AccessViolation`). Detectado y corregido en pruebas.

## 7. Pruebas realizadas

- `detectar` real: `{"modelo":"STU-540","pantalla":"800x480","sensor":"10800x6480"}`.
- `probar-pantalla` real: pantalla escrita, visible 6 s y limpiada.
- `capturar --timeout 15` real sin firmar: handshake DH + `StartCapture`
  aceptado + sondeo + `TIMEOUT` diseñado (prueba del camino cifrado completo).
- Dos `capturar --timeout 10` seguidos sin reconectar: ambos `TIMEOUT`
  diseñado (regresión del `rc=6` entre sesiones).
- `signatureService` vía `tests/hardware/stu_bridge.test.js` (helpers
  simulados, 6/6 OK): helper ausente, detectar, sobre con SHA-256, mapeo de
  error, respuesta inválida, timeout con proceso terminado.
- Suite `hardware_mocks` existente: 4/4 OK (sin regresiones).
- `pnpm run lint`: 0 errores. `pnpm run build:react`: compila.
- Pendiente manual (requiere firmar físicamente): `capturar` punta a punta
  desde Entregas/Órdenes → "Firmar en pad" → ACEPTAR en el pad → firma visible
